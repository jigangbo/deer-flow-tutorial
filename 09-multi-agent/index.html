    第 9 章 Multi-Agent 路由与子代理委派¶

    进阶篇第 4 章。第 6 章的中间件链里有这样一环：lead agent 的模型响应里可以出现 task 工具调用——"把这件事交给一个子代理去做"。子代理不是提示词角色扮演，而是 一个真正独立编译、独立事件循环、独立执行预算的 LangGraph 图，跑完把结果以 ToolMessage 形式写回父图。这一章拆解从 make_lead_agent() 组装、委派决策、 execution_id ↔ tool_call_id 关联链，到 task_* SSE 事件流与持久批处理的完整机制。

    9.0 学习目标¶

    读完本章，你应该能够：

    1. 画出 task() → SubagentExecutor.execute_async() → 隔离事件循环 → 轮询回写 ToolMessage 的完整委派时序，并说清 provider tool_call_id 与服务端 execution_id 各自负责什么、为什么必须分离；
    2. 解释 SubagentExecutionCapacity 的 FIFO 准入控制（max_running/max_queued/ admission_policy/queue_timeout_seconds）与 SubagentLimitMiddleware 的 每响应/每运行总额上限如何配合；
    3. 走读报告契约（report contract）与验收检查（acceptance checks）两层验证： [rN] 引用如何强制，file:<path> exists、tests_passed:<command> 这些叶子 判据如何在代码里判定、何时降级为 UNVERIFIED；
    4. 描述 task_started/task_running/task_completed/... 事件如何经 get_stream_writer() → StreamBridge → SSE 到达前端子任务卡片，又如何以 subagent.start|step|end 落入 RunEventStore 供刷新后恢复；
    5. 配置一条"研究员 + 评审员"双子代理流水线，观察委派、验收与结果回写全链路。

    9.1 概念：lead agent 与子代理的分工¶

    DeerFlow 是一个"超级 Agent harness"：一个 lead agent 负责对话、规划与综合， 把边界清晰、可独立完成的工作块委派给子代理。分工的判断标准写进了 agents/lead_agent/prompt.py:597 的路由策略段（模型可见）：

    ## Subagent Routing: Delegate Only for Clear Net Benefit

Subagents are optional. **Default to direct execution.** Do not delegate merely because a task is complex, has many steps, produces verbose output, or touches a large repository.

**DELEGATION CHECK (required before every `task` call):**

Expected benefit = ...（并行收益/专家能力/上下文隔离，按配置注入）

Expected cost = delegation and startup overhead + duplicate context and repository discovery + coordination and synthesis + state-conflict risk + side-effect risk

    subagents/AGENTS.md 把这套"benefit-based routing"提炼成工程规则：默认直接执行； 只有当并行延迟、专家技能或上下文隔离明显压过启动开销、重复发现、综合成本、 状态冲突与副作用风险时才允许 task；并行作用域要求输出独立、可变状态不相交； 每轮响应的委派上限为 1 时，只接受"实质性的专家/上下文收益"。

    子代理与父代理共享什么、隔离什么，一张表说清：

    维度 共享 隔离
    线程目录与沙箱 同一 (user_id, thread_id) 的线程数据与沙箱客户端 各自的租约 owner 与命令作用域（第 8 章）
    技能 技能投影目录 发现/激活白名单按子代理配置收窄
    身份与授权 user_id、user_role、authz 属性、trace id is_subagent=True 标记；ask_clarification 被剥离
    记忆 共享 thread id skip_memory_flush=True：子代理内部轮次不写入持久记忆
    事件流 父 run 的 SSE 通道 子图帧带命名空间，不冒充根帧（9.8 节）
    checkpoint 继承父的 checkpoint 命名空间坐标 checkpointer=False 编译，一次性执行、不可恢复

    9.2 源码走读：make_lead_agent 组装与容量决策¶

    9.2.1 图工厂入口的"薄外壳"¶

    backend/packages/harness/deerflow/agents/__init__.py:20：

    def make_lead_agent(config: "RunnableConfig") -> Any:
    """Build the lead graph while keeping package-root imports lightweight.

    LangGraph Server resolves configured graph factories directly from a
    module's ``__dict__``, so this entrypoint must be a concrete module-level
    function rather than a value supplied only through ``__getattr__``.
    """
    from .lead_agent import make_lead_agent as factory
    from .lead_agent.prompt import prime_enabled_skills_cache

    prime_enabled_skills_cache()
    return factory(config)

    两个设计约束在这里交汇：LangGraph Server 从模块 __dict__ 里直接解析图工厂， 所以入口必须是具体的模块级函数（不能是 __getattr__ 惰性导出）；同时 deerflow.agents 包根要保持轻量导入（backend/AGENTS.md 的 Import conventions 节）， 于是重型导入全部留在函数体内。prime_enabled_skills_cache() 在图构建前预热 技能缓存，避免第一轮对话付冷启动成本。

    9.2.2 容量解析：三层取最小值¶

    真正的组装在 agents/lead_agent/agent.py 的 create_deerflow_agent / make_lead_agent。子代理相关的一段（agent.py:709）：

        # Add SubagentLimitMiddleware to truncate excess parallel task calls
    subagent_enabled = cfg.get("subagent_enabled", False)
    effective_max_subagents_per_run: int | None = None
    if subagent_enabled:
        max_concurrent_subagents = effective_subagent_concurrency(
            cfg.get("max_concurrent_subagents"),
            resolved_app_config,
            execution_capacity=subagent_execution_capacity,
        )
        max_total_subagents = effective_total_subagents_per_run(cfg.get("max_total_subagents"), resolved_app_config)
        effective_max_subagents_per_run = max_total_subagents
        middlewares.append(SubagentLimitMiddleware(max_concurrent=max_concurrent_subagents, max_total=max_total_subagents))

    subagent_execution_capacity 来自启动时冻结的进程容量 （agent.py:991 的 configured_subagent_max_running()，读 capacity.py:182 的 启动快照）。并发上限按 subagents/AGENTS.md 的规则一次性解析为最小值： 每请求运行时覆盖、启动冻结的 subagent_runtime.max_running、schema 安全上限 （1–64）三者取 min，再同时喂给 lead 提示词（模型知道"我最多能并行几个"）与 SubagentLimitMiddleware（硬性截断多余调用）。热重载不可能让任何一层宣称 超过已创建的进程控制器容量——改了启动级配置必须重启才生效。

    _subagent_release_policy（agent.py:126）把最终生效的委派政策（含每个子代理 类型的 max_turns / timeout_seconds）作为 run 元数据发布，供扩展与调试观测。

    9.2.3 路由提示词里的硬限制¶

    prompt.py:597 起的路由段还包含非协商上限（模板变量按配置填充）：

    **HARD LIMITS - NON-NEGOTIABLE:**
- **MAXIMUM {n} `task` CALLS PER RESPONSE - NEVER emit more. VIOLATION IS A HARD ERROR.** Excess calls are discarded and their work is lost.
- **MAXIMUM {total} `task` CALLS PER RUN - NEVER exceed it. VIOLATION IS A HARD ERROR.** Count only delegations for the current user request/run; older thread history does not consume this run's allowance.

    SubagentLimitMiddleware 是这条提示词的执法者：当没有委派槽位剩余时，task 调用 被剥离、Provider 原始 tool-call 元数据同步、finish_reason 强制为 stop，并追加 一条可见的"subagent delegation limit"说明，让模型转向综合已有结果。每运行总额 上限由持久委派账本（delegation ledger）按当前 run 的条目核销——同线程更早 run 的历史委派不消耗本次预算；而显式 batch_task 走自己的持久限额，不占用也不 放宽普通账本。

    9.3 源码走读：execution_id ↔ tool_call_id 关联链（重点）¶

    这是本章最核心的一条线索。两个 ID 极易混淆，先给结论：

    • tool_call_id（provider ID）：模型输出的工具调用 ID，由 LangChain 注入 （task_tool.py:760 的 tool_call_id: Annotated[str, InjectedToolCallId]）。 它是 ToolMessage、task_* SSE 事件、前端卡片、ExtensionData.scope_id （SubagentResult.external_task_id）的关联键。
    • execution_id（server ID）：SubagentExecutor.execute_async 生成的 uuid4()（executor.py:2280），作为 SubagentResult.task_id 与进程内后台注册表 的键，拥有轮询、取消、超时与清理的全权。

    为什么必须分离？executor.py:2272 的 docstring 直说了：provider tool-call ID 在 不同父 run 之间会重复（task_id: Optional external correlation ID for logs. It is never used as the process-wide background registry key because provider tool-call IDs can repeat across concurrent parent runs.）。定时任务闭包保留自己的结果引用，绝不 通过可变注册表按 provider ID 找回所有权——这是 backend/AGENTS.md Runtime 节 "Subagent IDs"条目的硬性约定。

    9.3.1 委派起点：一次调用，两个 ID¶

    tools/builtins/task_tool.py:1110（委派与轮询的主干）：

        # Keep the provider tool-call ID for stream/message correlation, but use a
    # server-generated execution ID for process-wide background task control.
    execution_id = executor.execute_async(prompt, task_id=tool_call_id)
    if input_control is not None:
        input_control.bind_execution(tool_call_id, execution_id)

    # Poll for task completion in backend (removes need for LLM to poll)
    poll_count = 0
    last_status = None
    last_message_count = 0  # Track how many AI messages we've already sent
    # Polling timeout: execution timeout + 60s buffer, checked every 5s
    max_poll_count = (config.timeout_seconds + 60) // 5

    executor 侧（subagents/executor.py:2268）：

        def execute_async(self, task: str, task_id: str | None = None) -> str:
        """Start a task execution in the background.
        ...
        Returns:
            Unique execution ID that can be used to check status later.
        """
        execution_id = str(uuid.uuid4())

        # Create initial pending result
        result = SubagentResult(
            task_id=execution_id,
            external_task_id=task_id,
            trace_id=self.trace_id,
            status=SubagentStatus.PENDING,
        )

    SubagentResult（executor.py:120）因此同时携带两枚 ID：task_id（=execution_id， 服务端全权）与 external_task_id（=provider tool_call_id，仅供关联）。执行体随后 被提交到持久隔离事件循环（executor.py:2396 的 _submit_to_isolated_loop_in_context(parent_context, run_with_timeout)）——所有 native 子代理共享这一条循环与一个进程级 FIFO 容量控制器，排队者不占调度线程。

    9.3.2 关联链全景¶

    模型输出 tool_call（id=call_abc）

    同时，运行器把每条 task_* 自定义帧映射成 subagent.start|step|end 事件写入 RunEventStore（9.8 节），metadata 里带 task_id（provider ID）——刷新页面后 子任务卡片凭它回放步骤历史。

    9.3.3 终态回写：ToolMessage 与 additional_kwargs¶

                                # carry, which are root frames too.
                                llm_error_fallback_message = llm_error_fallback_message or _extract_llm_error_fallback_message(chunk, pre_existing_message_ids)

    根帧才允许影响父 run 的错误回退判定——子代理自己的模型故障由执行器映射为 task_failed，不会污染父 run 的终态。文件工具 chunk 批处理器、子代理事件持久化、 LLM 错误回退检测这三个"仅根帧"消费者在 backend/AGENTS.md Runtime 节里被列为 固定契约。

    9.7.4 前端：卡片与步骤时间线¶

    前端在 run 事件回调里把 task_* 帧转换为子任务卡片状态 （frontend/src/core/threads/hooks.ts:2306 附近）：

          const taskUpdate = taskEventToSubtaskUpdate(event);
      if (taskUpdate) {
        updateSubtask(taskUpdate);
      }

      if (eventType === "task_running") {
        const e = event as {
          type: "task_running";
          task_id: string;
          message: AIMessage;
          message_index?: number;
        };
        // Accumulate the full step history instead of overwriting (#3779): keep
        // latestMessage for the collapsed-header tool-call hint, and append the
        // normalized step (assistant turn or tool output) to the timeline.
        updateSubtask({
          id: e.task_id,
          latestMessage: e.message,
          steps: [messageToStep(e.message, e.message_index ?? 0)],
        });
        return;
      }

    task_running 是累加而非覆盖：助手轮与工具输出都进入时间线（#3779），卡片 折叠头显示最新工具调用提示。终态卡片的状态徽标从 ToolMessage.additional_kwargs 的 subagent_status/subagent_stop_reason 恢复——这正是"task_* 事件管实时、 ToolMessage 元数据管持久"的双通道分工。

    9.8 源码走读：持久批处理（subagent_batches）¶

    9.8.1 为什么要有 batch_task¶

    普通 task 的结果全量进入 lead 上下文；要并行跑几百个条目（如深度研报的分主题 检索）就需要"持久行 + 租约 + 预算上限"的运行时。batch_task 工具 （batch_task_tool.py:156）把条目交给 Gateway 侧的批处理服务，立即返回批次 ID， "it never inserts thousands of results into the lead agent context"——lead 用 batch_status 查进度、用 read_batch_result 按位置读单个条目。批模式是显式的， 绝不由提示词长度推断（subagents/AGENTS.md Flow 节）。

    提交侧的执行规格快照（batch_task_tool.py:249）值得注意：

        execution_spec = {
        "subagent_config": {**asdict(config), "prompt_overlay": config.prompt_overlay.model_dump()},
        "parent_model": metadata.get("model_name"),
        ...
        "is_internal": context.get("is_internal") is True,
        "authz_attributes": normalize_authz_attributes(context.get("authz_attributes")),
    }

    子代理配置（含 prompt overlay 的 JSON 序列化）、身份与授权属性被持久化—— 恢复的条目在 Gateway 重启后仍能以相同身份执行，且"知识范围/线程化身"等 上下文按 subagents/AGENTS.md 的边界原样继承、不可由模型输入放宽。

    9.8.2 租约心跳与恢复¶

    SubagentBatchService（batch_service.py:140）是租约感知的批次执行器：每个服务 实例持有 _lease_owner = f"{socket.gethostname()}:{uuid.uuid4().hex}" （batch_service.py:172），run_once 轮询（间隔 poll_interval_seconds，默认 1 秒） 认领到期条目。执行包装在 BatchItemLease（batch_lease.py:14）里——心跳每 lease_seconds/3 续租一次，__aexit__ 等心跳任务完全停止才返回，保证"续租写" 不会落在释放所有权之后。三条独立限额（config.example.yaml:2102）：

    键 默认 含义
    max_items_per_batch 5000 单批次持久条目总数
    default_max_live_items / max_live_items_per_batch 100 / 1000 同时 queued+running 的活条目窗口
    default_max_running_items / max_running_items_per_batch 3 / 64 单批次可占真实执行槽的条目数
    max_attempts 3 重试上限
    max_result_chars / result_preview_max_chars 100000 / 2000 结果存储与预览截断

    失败/过期租约消耗一次 attempt；队列拒绝/超时不消耗（subagents/AGENTS.md Flow 节）。用户取消使非终态条目终态化并清租约，旧 worker 的过期写入被 SQL 层的 owner/active 状态围栏挡住。

    9.8.3 批处理验收：无父运行时的复用¶

    batch_acceptance.py:27 的 check_batch_acceptance 让持久条目复用与 task 相同的 确定性检查——但批处理没有父工具运行时，于是它构造线程目录投影并自行获取沙箱 客户端租约：

        thread_id, user_id = batch["thread_id"], batch["user_id"]
    spec = batch["execution_spec"]
    context = {key: spec.get(key) for key in ("user_role", "oauth_provider", ...)}

    验收裁决（含 bash_executions 证据）随成功结果在同一租约围栏下持久化为可空的 result_artifact（migration 0033）；取消/失败/过期 attempt 不得发布证据，重试会 清除它。与 task 一致：验收不改变重试策略，succeeded 只表示执行完成。

    动手实验：配置"研究员 + 评审员"双子代理流水线¶

    目标：定义两个自定义子代理，让 lead 把"调研"与"评审"委派给不同专家，并观察 委派、验收与结果回写全链路。全程离线可复现（无需外部 API，只跑本地文件任务）。

    步骤 1：定义子代理（config.yaml，保持 Gateway 停机编辑或用 Gateway API 热改）：

    subagents:
  custom_agents:
    researcher:
      description: "收集并整理本地文件中的事实，输出要点清单"
      system_prompt: |
        你是研究子代理。只依据 /mnt/user-data/uploads 下的文件回答，
        用要点列出事实并注明来源文件名。不要编造。
      tools: [ls, read_file, grep, glob]
      max_turns: 30
      timeout_seconds: 300
    reviewer:
      description: "对照验收标准检查研究要点，输出通过/未通过清单"
      system_prompt: |
        你是评审子代理。对照任务给出的验收标准逐条核对研究结论，
        每条标注 holds/不成立，最后给出总结论。
      tools: [ls, read_file, grep, glob]
      max_turns: 30
      timeout_seconds: 300

  agents:
    researcher:
      skills: []          # 研究员不启用任何技能

    步骤 2：运行流水线。启动 make dev，新建会话，上传一份 notes.txt，然后 要求："先让 researcher 子代理总结 notes.txt 的三个要点（写出到 /mnt/user-data/outputs/findings.md），再让 reviewer 子代理对照验收标准 'file:/mnt/user-data/outputs/findings.md non-empty' 检查，最后汇总。"

    步骤 3：观察四条证据链：

    1. 委派：logs/gateway.log 里搜 Started background task——你会看到 task_id（provider ID）、execution_id（uuid）、子代理类型与轮询预算同行打印；
    2. 事件流：前端子任务卡片实时出现两个"研究员/评审员"卡片，task_running 步骤逐条追加（frontend/src/core/threads/hooks.ts:2312 的累加逻辑）；
    3. 验收：第二个 task 调用带 acceptance_criteria，完成后的结果文本尾部出现 验收清单段（acceptance_checks.py 渲染），每条叶子标 holds/UNVERIFIED； subagent_acceptance_verdict 同时写进 ToolMessage.additional_kwargs；
    4. 回写：刷新页面，卡片从 RunEventStore 的 subagent.start|step|end 事件恢复 步骤历史（不是从 SSE 重放）。

    步骤 4（可选）：观察容量上限。把 subagent_runtime.max_running 临时改为 1 （config.example.yaml:2012），重启后让 lead 一次并行委派两个子代理——第二个会 排队（max_queued: 64 内等待），日志出现容量等待；改回 3 恢复。若把 admission_policy 改为 reject，超出的 task 调用直接以 SubagentCapacityRejected 失败回写。

    常见坑¶

    1. 把 provider tool_call_id 当注册表键用。不同父 run 的 tool-call ID 会重复； 进程内一切控制（轮询/取消/清理）必须走 execution_id（SubagentResult.task_id）， provider ID 只做关联。跨 run 归因读 ToolMessage.additional_kwargs，不读全局缓存。
    2. 在子代理里期待 ask_clarification 或嵌套委派。内置与自定义子代理的 disallowed_tools 都排除 task/ask_clarification/present_files；定时任务等 非交互运行同理。子代理遇到信息不足应"带假设继续并在报告里写明"。
    3. subagent_runtime.max_running 改了却以为热加载生效。这是启动级配置： 进程控制器在启动时冻结，热重载不会让提示词或中间件宣称超过已建容量 （backend/AGENTS.md Concurrency 节），必须重启 Gateway。
    4. AIO 镜像 MAX_SHELL_SESSIONS 小于 max_running + 1。每个子代理作用域占一条 持久 shell 会话，lead 也要一条；会话耗尽的症状是命令报错。配置注释 （config.example.yaml:1851）要求显式值至少 max_running + 1，DeerFlow 会在 需要时自动注入满足值。
    5. 以为 completed 等于"验收通过"。task_completed 只表示执行终态；验收 逐条读 subagent_acceptance_verdict，UNVERIFIED 的判据没有被证明， subagent_stop_reason 还会告诉你这次完成是不是被预算截断的。路由提示词 也明确要求 lead"逐条读清单并保留有用工作"。
    6. 在 checkpoint 里恢复子代理。子代理图以 checkpointer=False 编译、一次性 执行；恢复对话时你能看到的是它的终态 ToolMessage 与持久化的事件历史， 而不是可续跑的子图。需要"续跑"语义请使用批处理的依赖与延续（continuation） 机制，而不是手工重放。
